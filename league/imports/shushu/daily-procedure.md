- 공통 자료의 최근 14일 DART 목록을 먼저 보고 실적·IR 등 이벤트를 확인한다. 기사만 있고 공시에서 확인하지 못한 내용은 `공시 미확인`이라고 표시한다.
- 출처의 기준일을 모르면 `확인 못함`, 월까지만 알면 `2026-10`처럼 확인한 범위만 쓴다. 받은 날짜를 기준일 대신 넣지 않는다.

## 5. CSV 검증과 원본 동결

아래는 운영자가 공지하고 2026-11-05 회신에서 지원을 확인한 명령 형식이다. 첫 실전에는 최신 `tools/league.py`로 해당 날짜의 파일을 실제 검증한다. 문서 수정만으로 명령을 실행·검증한 것은 아니다.

```bash
python3 tools/league.py schedule 2026-11-09 --to 2026-11-09
python3 tools/league.py import-csv league/imports/shushu/2026-11-09.csv --team shushu --dry-run
python3 tools/league.py commit league/imports/shushu/2026-11-09.csv
```

날짜는 실제 라운드로 바꾼다. `commit` 명령이 만든 `league/imports/shushu/<날짜>.sha256`을 사용하며, 지문 파일 문법을 임의로 만들지 않는다. `commit`은 지문 생성 절차이며, 이를 실행했다는 사실만으로 GitHub에 제출됐다고 보고하지 않는다.

동결 전 확인:

- CSV 헤더·UTF-8·활성 id·승인 버전·시장·대상 종목·중복·열린 시장 누락을 검증한다.
- `locked_at`은 실제 확정 시각이고 `+09:00`을 포함한다. 지문 push 시각보다 늦을 수 없다.
- 근거·위험·출처·기준일이 채워져 있으며 출처 확보 시각은 실제 관측값이다.
- 확인한 원 가격은 CSV의 `rationale` 등 근거에 쓸 수 있다. 기준 종가는 해당 라운드의 공식 기준 세션으로 통일한다(첫 실전은 KR·US 모두 11/6 종가). 장중 값이나 다른 날짜 종가로 대체하지 않는다. 화면·결과 묶음과 한 줄 대사에는 가격 숫자를 넣지 않는다. 채점은 운영자의 공식 자료를 따른다.
- 제출 대상 파일만 검증한다. 이미 accepted된 추천을 시험 삼아 다시 제출하지 않는다.

동결 후 보존:

- CSV 원본을 파일로 보존한다. 스프레드시트·텍스트 편집기로 열어 다시 저장하거나 내용을 복사해 새 CSV로 만들지 않는다.
- CRLF/LF, BOM, 인코딩, 열 순서, 따옴표, 공백, 마지막 줄바꿈을 포함한 **모든 바이트**가 지문 생성 때와 같아야 한다.
- 전송은 원본 파일 그대로 한다. 운영자 PC는 push 전에 `git pull`로 저장소의 `.gitattributes` 규칙 `league/imports/** -text`를 받아 제출 파일의 줄바꿈 자동 변환을 막는다. 운영자가 2026-11-05 이 조치와 바이트 보존 시험 결과를 확인했다.
- 원본을 커밋한 뒤 push하기 전에 `git show HEAD:league/imports/shushu/<날짜>.csv | sha256sum`의 해시와 `.sha256` 파일의 첫 64글자를 비교한다. 다르면 push하지 않고 동결 사본으로 다시 커밋한다. GitHub 웹 업로드를 쓰더라도 지문과 같은 원본 파일을 그대로 전달한다.
- 저장소에서 올릴 파일 목록을 확인해 지문 단계에는 `.sha256` 하나만 포함한다. 무조건 전체 폴더를 추가하는 방식은 쓰지 않는다.
- 동결한 CSV, 생성된 지문, 최종 토론 기록을 안전하게 보관한다. 토론 파일도 사후 분석으로 바꾸지 않는다.

| 원본 해시 불일치로 rejected | 동결 사본·Git 저장 바이트·전송 경로를 확인한다. 12:00 전에 **첫 지문과 일치하는 원본**을 다시 올린다. 새 지문 또는 사후 수정 내용으로 통과시키지 않는다. |
| 12:00까지 원본 미공개 | 미제출로 기록하고 원인을 남긴다. 소급 인정 없음. |
| 실수로 마감 전 CSV 공개 | `early_reveal` 사실을 즉시 운영자에게 알린다. 원장이나 기록을 삭제·수정해 숨기지 않는다. |
| 서비스·사용 한도·자료·전송 장애 | 실제 시각과 단계·영향을 남겨 운영자에게 보고한다. 장애 사유는 운영 측 장애 기록·화면에 반영하며 마감은 임의 연장하지 않는다. |
| 자료·주간 결정·승인 버전이 확인되지 않음 | 없는 데이터나 명단을 지어내지 않는다. 준비되지 않은 부분과 제출 영향만 정확히 보고한다. |

서버 push 시각을 확보하지 못할 때의 대체 시각·판정은 최신 엔진과 안내서의 v1.7 지문·원본 제출 규정에 따른다. 과거 규칙의 대체 기준을 새 제출 방식에 임의로 이식하지 않는다. 두 서버 시각 모두 확인되지 않은 제출을 자체적으로 정시 접수라고 판정하지 않는다.

## 7. 원본 접수 뒤 한 줄 대사 작성·검증·전달 (일일 실행 5단계)

### 7.1. 시작 조건과 대상

- **라운드 마감 08:30 KST가 지났고, 해당 원본 CSV 영수증이 `accepted`인 것을 모두 확인한 뒤** 시작한다. `committed`만 확인된 상태나 원본 접수가 보류·실패한 상태에서는 작성·전달하지 않는다.
- 실전 파일은 `league/lines/<날짜>-shushu.json`이다. 첫 실전 예시는 `league/lines/2026-11-09-shushu.json`이다.
- 파일 내용은 `{"pick_id": "문장"}` 형태의 JSON 객체다. `pick_id`는 `<날짜>-shushu-<에이전트>-<시장>` 형식이며, 예시는 `2026-11-09-shushu-s1-KR`이다.
- 접수된 해당 라운드의 **슈슈 팀 추천 전부**를 정확히 한 번씩 포함한다. 정상적으로 5명이 KR·US에 제출한 날은 10개이지만, 실제 접수된 활성 인원과 열린 시장을 기준으로 확인한다. 다른 날짜·다른 팀·존재하지 않는 `pick_id`를 추가하지 않는다.
- 같은 종목을 여러 에이전트가 추천했어도 `pick_id`마다 따로 쓴다. 로로 팀 대사는 쓰지 않는다.

### 7.2. 작성 기준

1. 해당 `pick_id`의 **접수된 CSV `rationale`에서 선택 이유 하나**를 고른다. 새 분석이나 마감 이후 정보를 추가하지 않는다. 대사를 위해 동결된 CSV·토론 기록을 고치지 않는다.
2. 캐릭터 말투의 **한 문장, 80자 이하**로 줄인다. 단단이는 듬직한 기사, 알짜는 똑 부러지는 보석 감정사, 돋보기는 증거를 따지는 탐정, 쑥쑥이는 신난 아이, 반전이는 장난꾸러기 말투를 참고한다. 반말도 가능하다.
3. **가격 숫자는 쓰지 않는다.** 원·달러·₩·$, 종가, 목표주가를 넣지 않는다. 증가율(%), 순위, 비유는 가능하지만 `rationale`에 없는 숫자나 확인되지 않은 사실을 만들지 않는다.
4. “무조건 오른다”처럼 수익을 약속하는 표현을 쓰지 않는다. 캐릭터 표현보다 근거의 사실성과 의미 보존을 우선한다.

### 7.3. 검사와 오류 수정

날짜를 실제 라운드로 바꾸고 저장소 루트에서 실행한다.

```bash
python3 tools/dashboard_data.py --check-lines league/lines/<날짜>-shushu.json
```

첫 실전 명령:

```bash
python3 tools/dashboard_data.py --check-lines league/lines/2026-11-09-shushu.json
```

- 출력에 **`통과`**가 나와야 한다. 실행 사실만으로 통과로 보고하지 않는다.
- 마감 전 작성, 라운드·팀이 다른 `pick_id`, 가격으로 보이는 표현, 80자 초과, 추천 누락 등 실패 원인을 수정하고 같은 명령으로 다시 검사한다.
- 검사와 별도로 모든 문장을 해당 CSV `rationale`와 대조해 사실·숫자·선정 이유가 일치하는지 확인한다. 검사 통과가 사실 검증을 대신하지 않는다.
- 통과 뒤 문장을 수정했다면 다시 검사한다. 오류가 남거나 검사를 실행하지 못했으면 통과본으로 전달하지 않고, 원인과 필요한 조치를 운영자에게 알린다.

### 7.4. 운영자 전달과 완료 확인

- 검사에 통과한 JSON 파일을 **운영자에게 직접 전달**하고, 대상 라운드·파일 경로·대사 수와 검사 결과 `통과`를 함께 남긴다. 운영자는 `league/lines/<날짜>-shushu.json`에 업로드한다.
- 가능하면 **12:00 전**에 전달하고, 늦어도 **해당 라운드 당일 KST 안에 업로드**되었는지 확인한다. 전달만 완료했거나 업로드 여부를 확인하지 못했다면 그 상태 그대로 기록한다.
- 대사의 지연·누락은 **점수·순위에 영향을 주지 않는다.** 없으면 화면에 기본 문구(“○○, 이번 판은 이걸로 간다!”)가 나온다. 대사 때문에 지문 제출이나 원본 공개·접수 확인을 늦추지 않는다.
- 검사한 최종 파일, 검사 결과, 실제 검사·전달·업로드 확인 시각을 보존한다. 원본 `accepted` 이후 대사 작업은 화면용 문구 작성 단계이며 추천 재선정이나 채점 수정 단계가 아니다.

### 7.5. 연습 시 경로

연습 파일은 `league/sandbox/lines/<날짜>-sandbox-shushu.json`이며, `pick_id`의 팀 값도 `sandbox-shushu`다. 실전 파일과 섞지 않는다.

```bash
python3 tools/dashboard_data.py --check-lines league/sandbox/lines/<날짜>-sandbox-shushu.json --base league/sandbox
```

## 8. 기록·주간 운영

- 추천 CSV, 토론, 출처, 실제 단계별 시작·종료, 지문·원본 해시, 커밋 SHA, 실행 ID, 두 단계 영수증, 한 줄 대사 JSON과 검사·전달·업로드 확인 기록을 보존한다.
- 기존 원장은 수정하지 않는다. 해시·채점 오류가 발견되면 원기록과 별도의 정정 기록을 남기는 운영 절차를 따른다.
- 토요일 복기는 잠정 점수를 구분하고, 확정되면 보완 기록을 추가한다. 원래 복기를 덮어쓰지 않는다. 주간 결과뿐 아니라 누적 성적과 확정·제출·기대·미제출·채점 전·보류 표본 수를 함께 본다.
- 지침 개선은 에이전트당 최대 3개, 반복된 판단 오류와 근거 pick_id 2건 이상을 기준으로 제안한다. 사용자 승인 전 새 버전을 적용하지 않는다.
- **규칙 v1.8:** 두 팀 현역 10명 통합 순위의 꼴등 1명만 교체한다(주당 최대 1명). 순위는 주간 확정 점수 평균 → 중앙값 → 최저점 순서이며, 완전 동점이면 교체를 보류한다. 팀 승패는 교체 대상 선정과 무관하다.
- 교체하려면 **각 팀의 확정 건수가 해당 팀 기대 제출 수의 60%(올림) 이상**이고, 꼴등의 확정 건수도 자기 기대 제출 수의 60%(올림) 이상이어야 한다. 기준 미달이면 교체를 보류한다. 채점 전·보류는 0점 처리하지 않고 평균에서 제외한다.
- 월요일 06:30 주간 마감의 `league/ledger/weekly_decisions.jsonl` 고정 기록에 따라 활성 인원과 대기 후보를 정한다. 첫 주간 마감은 2026-11-16 06:30이다. 꼴등이 나온 팀만 승인된 순서와 관점 제한에 따라 후보를 올리며 같은 날 07:05 분석부터 참가한다. 다른 팀은 교체하지 않는다. 쓸 후보가 없으면 빈자리로 두고 미제출로 세지 않는다. 대기 후보가 1명 남으면 다음 후보를 미리 제안해 승인을 받는다.
- 팀 주간 승패와 누적 비교는 **확정 종목의 종목당 평균**으로 한다. 합산점은 참고값이다.
- 점수는 모의 예측 점수이며 실제 매매 수익률·투자 권유가 아니다. 합산점은 포트폴리오 누적 수익률로 표현하지 않는다.
