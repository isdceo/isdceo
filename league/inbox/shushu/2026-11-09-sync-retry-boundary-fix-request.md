# 긴급 확인·수정 요청: 동기화 재시도 경계 3건

사용자 승인으로 전달합니다. 규칙·08:30 지문 마감·12:00 원본 공개 마감·채점 기준을 바꾸려는 요청이 아니라, 공지와 구현의 동작 및 복구 절차를 맞추기 위한 요청입니다.

검토 기준은 이 전용 저장소의 from-league 안전 사본 커밋 413c837bb3331a0aff4903809d6c808d0467978d입니다. 운영자 메인 저장소에는 접근하거나 수정하지 않았습니다. 아래 재현의 시각·activity·커밋 응답은 모두 합성이며, 실제 종목·가격·마감 전 상대 팀 자료·인증 정보는 없습니다. 실제 라운드에서 장애가 발생했다는 뜻은 아닙니다.

## 1. 08:30 이후 당일 원본의 재시도 종료·지연 알림이 다음 라운드로 밀림

대상:
- from-league/tools/shushu_sync.py:248–251 (_next_round)
- 같은 파일:411–426 (새 push 적용 실패의 rday 및 최종 판정)
- 같은 파일:735–744 (due_wakes의 _today 및 retrying)

재현:
1. 합성 activity의 원래 push 시각을 2026-11-09 09:00 KST로 두고, 허용 경로 submit/2026-11-09.csv를 해당 날짜의 reveal 작업으로 분류합니다.
2. 적용 단계에 TransientError를 주입하고 09:03, 09:05, 09:07, 12:00에 pull을 실행합니다.
3. 네 번 모두 retry이며 당일 taint가 없습니다. _retry_until(_next_round(pushed, cfg), cfg)는 2026-11-10 12:00 KST입니다.
4. 같은 기록을 대상으로 11:00의 due_wakes를 실행해도 당일 delay 알림이 없습니다.

기대:
- 날짜가 확인된 원본은 그 파일 라운드의 12:00까지 시간 기준 재시도하고, 끝내 처리하지 못하면 해당 라운드 운영자 확인 대기로 전환해야 합니다.
- 당일 원본의 통신 오류도 3회째 지연 알림에 포함되어야 합니다.
- 판정 시각은 원래 09:00 KST를 유지해야 합니다.

첫날 영향:
지문은 제때 냈고 원본만 08:30 이후 push한 경우, 당일 지연 알림이 누락되고 재시도 중 후속 push가 다음 날까지 대기할 수 있습니다. 마감 전 지문·원본 동시 push의 보류 해제 경로는 이 사례와 다릅니다.

## 2. 12:00 최종 오류 activity가 untaint 뒤에도 done으로 남음

대상:
- from-league/tools/shushu_sync.py:299–317 (done 및 activity 건너뛰기)
- 같은 파일:346–347 (최종 오류를 type=push로 기록)
- 같은 파일:903–910 (untaint)

재현:
1. 합성 08:20 push의 변경 파일 조회에 TransientError를 주입해, 당일 12:00에 최종 push/error와 taint를 기록합니다.
2. 운영자 확인 후 untaint 명령과 같은 형식의 기록을 추가합니다.
3. 통신 복구를 가정해 파일 조회·분류·적용을 성공 응답으로 바꾸고 12:05에 같은 activity로 pull을 실행합니다.
4. taint 집합은 비었지만 결과는 빈 목록입니다. 해당 activity가 done 집합에 있어 파일 조회와 적용 자체가 호출되지 않습니다.

기대:
운영자가 확인한 원래 activity/commit을 원래 push 시각으로 재개할 수 있어야 합니다. 같은 제출의 중복 접수 방지와 선택적 커밋 되살리기 방지는 유지해야 합니다. 별도 복구 절차가 필요하다면 untaint 안내와 공지에 그 절차를 명확히 적어 주세요.

첫날 영향:
공개 마감까지 통신 오류가 이어진 후 확인 대기를 풀어도 원래 제출이 자동 복구되지 않을 수 있습니다.

## 3. 비교기준 before 커밋의 timeout이 비일시오류로 분류됨

대상:
- from-league/tools/shushu_sync.py:140–157 (_changed의 fetch 오류 수집 및 비교기준 fallback)

재현:
1. after는 로컬에 있고 before는 없게 구성합니다.
2. before를 받는 _fetch는 timeout을 반환하고, fallback HEAD는 after와 같도록 합성 git 응답을 줍니다.
3. _changed는 TransientError가 아닌 비교 기준 없음 RuntimeError를 발생시킵니다.
4. 이 예외 분류는 pull에서 12:00까지 재시도가 아니라 MAX_TRIES=3 최종 오류 경로로 들어갑니다.

기대:
통신 오류 때문에 비교기준을 아직 못 받은 상황과, 실제로 커밋·비교기준이 사라진 상황을 구분해 주세요. 전자는 공지한 시간 기준 재시도를 보장해야 합니다.

첫날 영향:
이 조건의 일시적인 통신 오류는 3회만에 최종 실패가 될 수 있습니다.

## 함께 확인한 정상 동작

- 08:30 전 push의 통신 오류는 4회 이상이어도 당일 12:00 전에는 계속 재시도하고, 12:00 최종 오류 때 해당 라운드를 확인 대기로 둡니다.
- 재시도 중인 앞 push가 있으면 뒤 push는 적용하지 않습니다.
- 같은 activity 재실행은 중복 처리되지 않습니다.
- 실제 임시 git 저장소 2개를 이용한 합성 지문 시험에서, 08:20 push를 11:00에 처리해도 영수증은 committed 및 원래 08:20을 유지했습니다. 뒤의 다른 합성 지문은 첫 지문을 덮어쓰지 않았고 원장 해시 체인도 정상이었습니다.

첫 라운드 동기화에 영향을 줄 수 있어 긴급 확인과 수정, 수정 후 위 경계의 회귀 시험 결과 회신을 요청합니다. 변경이 공지한 동작을 넘어 규칙·공정성·권한 변경을 필요로 한다면 별도 운영자 승인 사항으로 분리해 주세요.
