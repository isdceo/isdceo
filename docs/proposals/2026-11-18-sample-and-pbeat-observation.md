# 개선안 — 최소 표본 관찰판, p_beat·관망 설명 확인 (2026-11-18, 2차 초안)

운영자 요청("정리해", 2026-11-18). ZhuLinsen/daily_stock_analysis(MIT) 검토에서 나온 아이디어 두 가지와 그에 대한 검토 의견을 반영했다. 코드는 가져오지 않는다.

**상태: 제안. 아무것도 바뀌지 않았다.** 둘 다 점수·순위·탈락·제출 판정에 영향이 없는 **관찰**부터 시작한다. 실행은 따로 운영자 승인을 받는다. v2.2는 아직 확정되지 않았으므로 지금 규칙을 그대로 유지한다.

## 0. 원본에서 확인한 것 (사실)

참고 코드: `src/services/decision_signal_outcome_service.py`(클론 시점 커밋 `a36c824`; 검토 의견은 `3acb2c5` 기준).

- **완료 표본 기준이 둘이다.**
  - 복기 메모리 `MIN_REVIEW_SAMPLE_SIZE = 10`: 10건 미만, 평가 불가 50% 초과, 데이터 품질 낮음 중 하나면 '관찰만'.
  - 성향별 보정 `MIN_PROFILE_CALIBRATION_SAMPLE_SIZE = 30`.
  - 어느 쪽도 그 숫자가 통계적으로 충분하다는 뜻은 아니다.
- **원본에 있는 어긋남 검사:** "점수 60 이상인데 결론이 관망(또는 40 미만인데 관망)이면 이유가 있어야 한다"는 규칙이다(`docs/decision-signals.md`).
  - 원본은 이유가 없으면 행동을 점수에 맞춰 다시 정렬하기도 한다. 이번 제안처럼 기록만 하는 것과는 다르다.
  - `p_beat`와 관망을 직접 비교하는 검사는 원본에 없다. 3장은 우리 방식으로 넓힌 아이디어다.

## 1. 우리 리그의 조건

- **표본이 느리게 쌓인다.** 에이전트 하나가 한 시장에서 주(월~금)에 낼 수 있는 표본은 최대 5건이다. 10건이면 2주 이상, 30건이면 6주 이상 걸린다. 탈락·교체·지침 버전 변경으로 같은 조건의 표본은 더 줄어든다.
- **같은 날 결과는 서로 엮인다.** 같은 라운드 종목들은 시장 전체 움직임을 함께 탄다. 종목 수가 아니라 **서로 다른 라운드 수**를 같이 봐야 한다.
- **`p_beat`는 로로 팀에만 있다.**
  - 로로 라운드 기록(`league/rounds/<날짜>/claude/final.json`)에만 있고, 두 팀 공통 제출 CSV에는 칸이 없다.
  - 두 팀 공통 검사로 하려면 CSV 칸을 추가해야 하고, 이는 규칙 변경이다.
  - 로로 쪽 정의: "평가 종가(라운드 당일 종가)에 그 시장 지수(KR = KOSPI, US = SPY)를 이길 확률(0~1 소수), 기간은 하루"(`.claude/skills/league-round/SKILL.md`).

## 2. 최소 표본 관찰판 (2번)

**목적:** 주간 복기에서 성과 숫자를 볼 때, 그 숫자가 몇 건·몇 라운드에서 나왔고 무엇이 빠졌는지 함께 보이게 한다.

- **집계 단위:** 팀 × 에이전트 × 시장 × 지침 버전. 주간과 누적을 따로 낸다.
- **두 축으로 나눠 센다(같은 종목을 두 번 세지 않는다):**
  - 선택 유형: 실제 종목 / 관망
  - 채점 상태: 확정 / 채점 대기 / 보류(평가 불가, 사유별) / 무효
  - 표는 '유형 × 상태' 칸으로 만든다. 예를 들어 '확정된 관망'은 한 칸에만 들어간다.
- **미제출은 따로 센다.** 제출이 없으니 위 두 축에 들어가지 않는다. 그 라운드에 그 시장이 실제로 열렸고, 그 에이전트가 그 리그 출전 명단에 있었을 때만 1건으로 센다. 기준은 당시 명단이다(합류·탈락 주 반영, 지금 `weekly`의 `expected` 계산과 같은 기준).
- **채점 규칙 구간을 나눈다.** 같은 지침 버전이라도 관망 채점 규칙이 다르면 섞지 않는다. 예: v1.9·v2.0의 지수 수익률 관망, v2.2(스위치가 켜지면 `rule_locks` 고정값 기준)의 0% 관망.
- **두 팀 같은 기준:** 같은 집계 시각(예: 주간 마감 06:30)에 같은 원장을 쓰고, 정정(`correction_of`)은 최신 값으로 반영한다. 정정 건수는 따로 보인다.
- **함께 보이는 값:**
  - 서로 다른 라운드 수
  - 확정 표본의 평균·중앙값
  - 주간 표에는 실제 건수만, 누적 표에는 표본 구간('10건 미만', '10~29건', '30건 이상')을 함께 표시한다. 표시만 하고 판정에 쓰지 않는다. 10건이나 30건이 신뢰도를 보장하지는 않는다.
- **하지 않는 것:**
  - 숫자만 채워 지침을 자동으로 바꾸지 않는다.
  - v2.1 주간 개선 절차(1위 동결, 새 버전 냉각, '같은 유형 오류 pick_id 2건 이상', 운영자 승인)는 그대로다.
  - 표본 구간은 개선안의 참고 근거로만 적는다.
- **범위:**
  - 공통 원장으로 두 팀을 **같은 정의**로 집계한다(점수 영향 없음).
  - 화면 공개 전에 슈슈 팀에 정의를 먼저 알린다.
  - 로로 주간 복기(`league-review` 2-0단계 숫자 점검)에 먼저 붙인다.

## 3. p_beat·관망 설명 확인 (3번, 로로 팀만)

### 3-0. 먼저 정할 것: 관망의 `p_beat`는 무엇의 확률인가

지금 로로 기록의 관망 9건(11/16~11/18)은 모두 `p_beat = 0.50`, `exp_excess = 0.0`이다. 이 값은 실제 확률이 아니라 **'중립'을 뜻하는 관례값**이다.
- **v1.9·v2.0 규칙에서:** 관망은 지수와 같은 수익률이고 초과 점수가 정확히 0이다. 그래서 "관망이 지수를 이길 확률"은 정의상 0이다.
- **v2.2 규칙(확정되면)에서:** 관망 초과 점수는 −지수 수익률이다. "관망이 지수를 이길 확률"은 "그날 지수가 내릴 확률"과 같다.
- **선택하지 않은 후보 종목의 확률일 수도 있다.** 이 경우에는 어느 종목인지 따로 적지 않으면 뜻이 없다.

제안(로로 팀 지시 변경, 운영자 승인 필요):
- `p_beat`·`exp_excess`는 **실제 종목에만** 적는다. 관망이면 `null`(해당 없음)로 둔다.
- 관망 판단의 근거로 후보 종목의 확률을 쓰고 싶으면 `cand_ticker`와 `cand_p_beat`를 따로 적는다(같은 정의: 그 후보가 그날 지수를 이길 확률).
- 기존 관망의 0.50 값은 고치지 않는다(원장·기록 불변). 집계할 때 '관례값'으로 표시해 실제 확률과 섞지 않는다.

정의가 정해지기 전에는 3번 점검을 시작하지 않는다.

**목적:** 확률과 결론이 달라 보일 때 그 이유가 적혀 있는지만 본다. 지수를 이길 확률이 높아도 손실 위험이나 근거 부족 때문에 관망할 수 있으므로, **자동으로 모순이라고 판정하지 않는다.**

- **대상과 시점:** 로로 라운드의 `final.json`. **원본 접수(`accepted`) 뒤**에 한다. 실시간 제출(지문 08:30, 원본)을 늦추지 않는다.
- **기록 양식:** 모든 관망과 아래 경우에 같은 양식을 쓴다. 칸은 pick_id, 유형, `p_beat`(또는 `cand_ticker`·`cand_p_beat`), 이유 문장 유무, 정의 혼동 여부다.
- **찾는 경우:**
  1. 관망인데 `cand_p_beat`가 높게 적힌 경우
  2. 종목을 냈는데 `p_beat < 0.50`인 경우
  3. 실제 종목인데 `p_beat`가 비었거나 형식이 틀린 경우(지금 점검 항목 그대로), 관망인데 `p_beat`에 값이 적힌 경우(정의 혼동)
- **하는 일:** 근거(`rationale`)에 이유 문장이 있는지만 `timing.json` 메모나 별도 기록에 적는다.
  - 감점·거부·재작성 요구는 하지 않는다.
  - 에이전트 판단도 바꾸지 않는다(진행자 원칙 그대로).
- **검토 대상:** 이유가 없거나 정의가 불명확한 경우만 본다.
- **'높게'의 기준값:** 정하지 않는다. 지금 지침의 `p_beat`는 보통 0.50~0.57이다.
- **2~3주의 의미:** 성과를 입증하는 기간이 아니다. 운영할 수 있는지와 오탐이 얼마나 나오는지 확인하는 기간이다.
- **주간 복기:** 표시된 사례를 보고 '이유 있음 / 이유 없음 / 정의 혼동' 건수만 센다.

## 4. 순서

0. **우선순위:** v2.2 준비와 매일 정상 제출이 먼저다. 이 실험은 그 뒤에 한다.
1. **운영자 승인 뒤:**
   - 2번을 로로 주간 복기 자료에 추가한다(두 팀 같은 정의, 점수 영향 없음).
   - 3-0 정의를 로로 라운드 지시에 넣는다.
   - 3번을 원본 접수 뒤 기록 전용 점검으로 추가한다.
2. **2~3주 관찰:** 실제 사례, 오탐, 표본 구간 분포를 정리한다.
3. **그 결과로 공통 규칙 후보를 슈슈 검토에 올린다.**
   - 후보: 공통 CSV에 `p_beat` 칸 추가, 표본 구간 표시 방식.
   - v2.2·2단계 일정이 확정된 뒤로 한다. 공통 적용은 두 팀 검토, 운영자 승인, 적용일이 필요하다.
4. 로로 팀 자체 실험과 두 팀 공통 적용은 문서·공지에서 늘 구분해 적는다.

## 5. 검토 의견 반영 내역 (2026-11-18)

- 10건 기준은 특정 기능의 기준이고 다른 통계는 30건이며, 어느 쪽도 충분성을 뜻하지 않는다는 점을 적었다(0장).
- 상태를 나눠 집계하고 시장·버전으로 나누며, 같은 날·같은 종목의 연관을 고려해 라운드 수를 함께 보이게 했다(1·2장).
- 자동 지침 변경을 금지하고, 동결·냉각·승인 절차를 유지한다(2장).
- `p_beat`·관망을 자동 모순 판정하지 않고, 이유 확인과 기록만 하며, 감점·거부는 하지 않는다(3장).
- `p_beat`의 기준 지수와 기간을 명시했다(1장).
- 시범 관찰 → 사례·오탐 확인 → 공통 규칙 제안 순서로 정했다. 로로 자체 실험과 공통 적용을 구분하고, v2.2 미확정 상태에서 지금 규칙을 유지한다(4장).

### 2차 검토 반영 (2026-11-18)

- 상태(확정·대기·보류·무효)와 선택 유형(종목·관망)을 두 축으로 나눠, 확정된 관망을 두 번 세지 않게 했다.
- 미제출은 실제 개장일과 당시 출전 명단 기준으로 센다.
- 관망 채점 규칙이 바뀌면 같은 버전 안에서도 구간을 나눈다.
- 두 팀 같은 집계 시각과 정정 반영 방식을 쓴다. 주간에는 실제 건수, 누적에는 10·30건 구간을 보인다(신뢰도 보장 아님).
- 관망의 `p_beat` 정의 문제를 3-0에 정리했다. 실제 종목에만 적고, 관망은 `null`, 후보 확률은 따로 적는다. 정의가 정해지기 전에는 시작하지 않는다.
- 점검은 원본 접수 뒤에, 같은 양식으로 기록만 한다. 이유 없음·정의 불명확만 본다. 2~3주는 운영 가능성과 오탐을 확인하는 기간이다.
- 원본의 점수·관망 어긋남 규칙이 이유가 없을 때 행동을 다시 정렬한다는 차이를 0장에 적었다.
- v2.2 준비와 매일 제출을 우선한다.
