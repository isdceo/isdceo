## 1. 봉인 원본의 최종 release 오류가 untaint 뒤에도 복구되지 않음

### 재현
1. 08:18 push에 당일 원본 파일이 있다고 분류합니다. 08:21 `pull()`에서 원본은 08:30까지 `held`로 기록됩니다. 실제 CSV나 종목 없이 파일 종류·날짜만 합성합니다.
2. 12:00 보류 해제 때 `_restore_held()`가 `TransientError`를 내게 합니다.
3. 최종 기록이 `type="release", status="error", transient=true`가 되고 해당 라운드는 확인 대기가 됩니다.
4. 운영자 해제를 나타내는 같은 라운드 `untaint` 기록을 추가합니다.
5. 소스가 복구됐다고 가정해 복원·적용 함수를 정상으로 바꾸고 12:05에 같은 활동으로 `pull()`을 다시 실행합니다.

### 예상
보류 중이던 원본을 원래 08:18 push 시각으로 한 번 복구하고, 성공 뒤 재실행에는 중복 접수하지 않아야 합니다.

### 실제
확인 대기만 풀리고 `pull()` 결과는 빈 목록입니다. 복원·적용 호출이 0회여서 원본이 복구되지 않습니다.

### 근거
- 469~470행: 최종 보류 해제 오류를 `type="release"`로 기록합니다.
- 333행: 성공 여부를 구분하지 않고 모든 `release`의 held_id를 완료 집합에 넣습니다.
- 273~284행의 `_reopened()`는 `push`만 다시 열고 `release`는 다루지 않습니다.
- 독립 시험: `test_14_hold_release_retry_terminal_recovers_after_untaint`, 예상 적용 1회 / 실제 0회.

요청: 운영자 해제 후 최종 일시 오류 release도 안전하게 재개할 수 있게 하고, 성공한 release와 비일시 오류를 잘못 다시 열지 않는 회귀 시험을 추가해 주세요.

## 2. 복구 후 비일시 오류로 확정돼도 과거 untaint 때문에 계속 재시도됨

### 재현
1. 08:18 push를 08:21·08:23·08:25에 일시 오류로 재시도합니다.
2. 12:00에도 같은 일시 오류를 내 최종 오류·확인 대기로 만듭니다.
3. 운영자 `untaint`를 추가합니다.
4. 12:05 재처리에서는 `RuntimeError("synthetic not our ref")`를 내게 해 비일시 최종 오류로 확정합니다.
5. 새 `untaint` 없이 12:06에 다시 `pull()`을 실행합니다.

### 예상
가장 최근 오류가 비일시 최종 오류이므로 처리 대상을 다시 열지 않아야 합니다. 12:06의 결과는 빈 목록이고 비교 함수도 다시 호출되지 않아야 합니다.

### 실제
12:06에도 같은 push를 다시 처리하고 최종 오류를 한 줄 더 남깁니다. 원장의
`일시 최종 오류 → untaint → 비일시 최종 오류`
순서만으로 `_reopened()`가 해당 activity_id를 계속 반환하는 것도 별도로 재현했습니다.

### 근거
- 278~281행은 새 일시 최종 오류 또는 오류가 아닌 push에서만 재개 상태를 지웁니다.
- 새 비일시 최종 오류는 이 두 분기에 들어가지 않아 이전 `untaint`의 재개 상태가 남습니다.
- 독립 시험: `test_18_nontransient_failure_after_reopen_stays_closed`, 예상 재실행 없음 / 실제 오류 재처리.

요청: activity별 가장 최근 확정 상태가 우선하도록 처리하고, 비일시 오류가 확정된 뒤 과거 해제 기록으로 자동 재개되지 않는지 확인해 주세요.

## 3. 수정 전 형식의 최종 일시 오류 기록은 untaint로 복구되지 않음

### 재현
수정 전 코드가 남기던 다음 형태의 기록을 합성 원장에 둡니다. `round`, `wake_round`, `taint_rounds`는 없는 형식입니다.

```json
{
  "repo": "synthetic/repo",
  "type": "push",
  "activity_id": "1",
  "status": "error",
  "transient": true,
  "s_after": "0000000000000000000000000000000000000001",
  "pushed_at": "2026-11-09T08:18:00+09:00",
  "at": "2026-11-09T12:00:00+09:00"
}
```

1. 같은 activity_id의 `type="taint", team="shushu", round="2026-11-09"` 기록을 추가합니다.
2. 해당 라운드의 운영자 `untaint`를 추가합니다.
3. 비교·분류·적용을 정상으로 두고 12:05 `pull()`을 실행합니다.

### 예상
이미 남아 있는 구형 오류도 운영자 확인 후 안전한 복구 경로가 있어야 합니다. 라운드를 안전하게 판별할 수 없다면 그 한계가 명시돼야 하며, 확인 대기만 풀린 채 성공한 것처럼 끝나면 안 됩니다.

### 실제
`_reopened()`가 `round` 없는 오류를 대상에 넣지 않아 `done`에 그대로 남습니다. 처리 결과는 빈 목록, 적용 호출은 0회입니다.

### 근거
- 278행의 `and x.get("round")` 조건.
- 독립 시험: `test_15_preupgrade_terminal_push_can_recover`, 예상 복구 1회 / 실제 0회.
- 구형 형식으로 실패가 발생하는 것은 합성 검증으로 확인했습니다. 영향받는 실제 운영 기록이 존재하는지는 확인하지 않았습니다.

요청: 구형 최종 일시 오류 기록에 대한 호환 처리 또는 안전한 마이그레이션·운영자 복구 절차를 마련해 주세요. 실제 영향 기록이 없다면 그 확인 결과도 회신 부탁드립니다.
